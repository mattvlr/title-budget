Three things worth knowing

The projection belongs in the UI, before the button

The number is trivial to compute and it is the only thing standing between a user and a surprise bill. Showing it afterwards is an apology, not a feature.

Make the budget a hard stop on requests, not a counter

Check and refuse before the call goes out. A counter you inspect afterwards has already spent the money. And the number you show the user should be the number they were billed for — if those two can drift apart, they will.

Decide what a half-finished run is worth

When the budget runs out mid-way you can keep the partial tree or throw it away. Both are defensible. What is not defensible is not having decided, because the calls are spent either way.

A trap worth naming. If your app has a demo or offline mode that skips the API, your budget tests probably pass without proving anything — the demo path never spends, so the cap is never exercised. Stub the client and count actual outbound requests instead. A test that cannot fail is not evidence.
