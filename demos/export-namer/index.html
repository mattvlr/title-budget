Every filename below was generated by running the product's own naming core under Windows Script Host at //E:jscript — the same ES3 language level ExtendScript uses. The same eight layer names go into all five templates. Nothing here was typed by hand or edited afterwards.

tokens used: doc name

Deliberately wrong, and shown on purpose. There is no camel or pascal modifier. An unrecognised one returns the value unchanged, so this looks like it worked and did not — the spaces are still there. The four real modifiers are kebab, snake, lower and upper, plus numeric zero-padding.

What is verified, and what is not

  • 46 assertions pass on the naming logic — every token, every modifier, the padding, the collision handling and the illegal-character rules. They run at the same ES3 level ExtendScript uses, so a construct that would fail inside Adobe fails in the harness too.
  • 16 static checks pass on the adapter — it parses at ES3, uses no ES5 built-in that ExtendScript lacks, and calls only functions the core exports.
  • The adapter has never been run inside Photoshop or Illustrator. There is no Adobe installation on the machine this was built on. The tables above exercise the naming core, which is the half that can be tested outside Adobe; the adapter is the half that cannot, and it is unproven. The harness says so itself when you run it.
  • That is why it ships in dry-run mode. The first run lists the filenames it would write and exports nothing, so finding out costs you nothing.
